# تقوية أمان جدول `spaces` (جاهز للمراجعة — لم يُنفَّذ شيء)

**المشكلة (تقرير 2026-10-03):** مفتاح `anon` المنشور بالتطبيق يستطيع قراءة صفوف `spaces` كلها، فكود المزامنة (6 رموز) ليس سراً.

**الحل المقترح بلا تسجيل دخول:** منع الوصول المباشر للجدول وجعل الوصول عبر 3 دوال تأخذ الكود (`get_space` / `put_space` / `peek_space`).
المستخدم الذي يعرف الكود فقط يقرأ/يكتب صفّه، ولا أحد يقدر **يسرد** كل الصفوف.

## الخطوات بالترتيب (كل خطوة قابلة للتراجع)
| # | الملف | ماذا يفعل | آمن؟ |
|---|---|---|---|
| 1 | `01-readonly-audit.sql` | استعلامات قراءة فقط. أرسل لي الناتج (بدون بيانات مستخدمين). | ✅ قراءة فقط |
| 2 | `02a-create-rpc.sql` | ينشئ الدوال الثلاث فقط. التطبيق الحالي يبقى يعمل. | ✅ إضافة فقط |

## حدود الحل (للشفافية)
- الكود يبقى "سراً بالمعرفة": من يخمّنه يصل لبيانات صاحبه. 6 رموز من 31 حرفاً ≈ 887 مليون احتمال، ولا يوجد تحديد معدل (rate limit) على الدوال.
  توصيتي لاحقاً: كود أطول (12 رمزاً) للمستخدمين الجدد، وربما تسجيل دخول Supabase Auth لمن يريد خصوصية كاملة.
- **ملفات Storage** (`course-files`): لم أغيّر شيئاً. إذا كان الـ bucket عاماً فأي شخص يعرف المسار الكامل يقرأ الملف. القفل الكامل يحتاج
  روابط موقّعة (signed URLs) وتغيير سياسات `storage.objects` — مرحلة ثانية بعد مراجعة ناتج الاستعلامات (6 و8).
- لا أستطيع تنفيذ SQL من هنا (لا وصول إدارياً)، ولن أنفّذ أي ملف منها دون موافقتك الصريحة وتشغيلك له.

## التراجع الكامل
`02c-rollback.sql` يعيد الوصول المباشر. وإيقاف وضع RPC بالتطبيق: `CFG.useRpc = false`.
